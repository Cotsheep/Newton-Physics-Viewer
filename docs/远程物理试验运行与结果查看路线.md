# 远程物理试验运行与结果查看路线

状态：设计基线
适用项目：Newton-Test
目标环境：私有 Linux NVIDIA GPU 服务器，通过 Tailscale 从本地访问

## 1. 当前目标

第一阶段只打通下面这条最短闭环：

1. 操作者使用管理员批准的现有普通 SSH 路径，以个人集群账号启动一个批准的物理试验；
2. 服务器使用 Newton 和 NVIDIA GPU 无头执行试验；
3. 试验持续生成低频预览，并在完成后生成结果录像和其他产物；
4. 操作者通过本地浏览器和按需 SSH 隧道查看这些结果；SSH 连接本身经现有 Tailscale
   私有地址到达服务器。

这里的“本地查看”只包含运行中的低频预览，以及完成后的录像、截图、日志和运行清单。
它不包含从浏览器控制 Viewer 的相机、关节、夹爪或拖拽交互。Tailscale 只提供私有网络
路径，不负责传输 `view.py` 的原生桌面窗口。

第一阶段不建设通用 Web 任务平台，也不承诺从浏览器创建、排队、取消或管理试验。

### 1.1 开发与部署环境

第一阶段不创建或共享专用 `newton-runner` 账号。远程试验作业和结果目录均属于操作者的
个人集群账号；该账号不因本项目获得额外 `sudo` 或其他用户目录权限。资产目录保持只读，
结果只写入个人账号获准使用的 `NEWTON_DATA_ROOT`。

代码先在本地 WSL 中实现和测试，再进入远程服务器验收。2026-08-07 的本机探针结果是：

- WSL2 Ubuntu 24.04.1 已安装，systemd 正常运行；
- 仓库可以从 `/mnt/d/code/PythonProjects/Newton-Test` 访问；
- WSL Python 3.12 尚未安装 Newton、Warp、MuJoCo 或 USD Python 包；
- Windows 主机只有 Intel Arc 图形设备，WSL 没有 NVIDIA/CUDA 设备或 `nvidia-smi`；
- WSL 镜像网络配置启动失败并退回无网络，需要在安装依赖前解决。

2026-08-07 的远程只读探针已确认：

- 可以通过 Tailscale 地址和现有 OpenSSH 公钥认证进入 Ubuntu 22.04.5 LTS；
- 未安装 Slurm/PBS 客户端命令，不按受管理调度集群设计；
- systemd 不是 PID 1，`systemctl --user` 离线，因此不能使用 systemd user service 或
  linger；
- `systemd-detect-virt` 确认为 Docker，PID 1 是前台 `sshd`；
- 未安装 supervisor；`tmux` 与 `setsid` 可用，可作为无 systemd 环境的候选托管基础；
- Tailscale、FFmpeg 和 NVIDIA 工具已安装；
- Tailscale 版本为 1.96.4，当前尚无 Serve 配置；
- 当前直接可见七块 NVIDIA GeForce RTX 3090，每块 24 GiB，驱动为 575.57.08；
- 系统默认 Python 为 3.10.12，项目仍需用 `uv` 在个人目录提供锁定的 Python 3.12 环境。
- 个人目录是 `/dev/sda` 上的独立 ext4 挂载，不是容器 overlay；探针时总容量约 55 TiB、
  已使用 90%、剩余约 5.6 TiB；

远程环境已确认是无 systemd 的 Docker 实例，不能套用 linger。第一阶段正式执行后端确定在
现有普通 SSH 连接上使用本地控制程序与远程编排器的工况边界协议；控制端失联时允许当前
工况完整收尾，但不得启动下一个工况。第一阶段不使用 `tmux`、`setsid` 或自建后台守护
进程。结果目录放在个人 ext4 挂载内，但其备份、配额和容器重建后的重新挂载仍需遵守
服务器管理员说明。

本地开发采用 WSL 默认、较简单的 NAT 网络，不依赖镜像网络。计划把用户级
`.wslconfig` 调整为：

```ini
[wsl2]
networkingMode=nat
dnsTunneling=true
firewall=true
autoProxy=false
```

变更后执行一次 `wsl --shutdown` 并重新启动 Ubuntu，再分别验证默认路由、DNS、HTTPS
下载以及 Windows 浏览器访问 WSL 本地测试页。该操作会停止所有正在运行的 WSL 进程，
只能在明确执行维护步骤时进行；路线图确认本身不立即修改用户系统。项目不通过关闭 Windows
或 WSL 防火墙来解决网络问题。

本地目录按职责分离：

- 唯一源码工作树继续位于 `/mnt/d/code/PythonProjects/Newton-Test`，不再维护第二份 WSL
  源码副本；
- Python 虚拟环境、包缓存和本地冒烟结果放在 WSL 的 ext4 文件系统；
- `NEWTON_DATA_ROOT` 在 WSL 中指向源码目录之外的专用测试数据根目录；
- 只有挂载盘性能或 Linux 文件语义成为实测问题后，才重新评估把源码迁入 WSL。

正式远程控制程序默认从 Windows CMD 运行。它是一个不依赖 Newton 的纯 Python 小程序，
通过 `subprocess` 调用 Windows 自带的 `ssh.exe`：

- 使用 `ssh -T <alias> <fixed-command>` 建立不分配伪终端的结构化控制通道；
- `<alias>` 只定义在 Windows 用户自己的 `.ssh/config` 中，由该配置保存服务器地址、
  用户名和私钥路径；
- 仓库、运行请求、日志和结果清单只记录 SSH 别名，不保存真实 Tailscale 地址、服务器
  用户名或私钥路径；
- 保持正常的 SSH 主机密钥校验，不使用 `StrictHostKeyChecking=no` 绕过身份确认；
- 控制协议通过标准输入和标准输出传递结构化消息，普通日志写入标准错误和 `run.log`；
- Windows 控制程序收到 `Ctrl+C` 后先发送取消消息，并等待远程端完成当前进程组终止与
  状态收尾；
- WSL 只测试控制协议、参数校验和错误路径，不复制 Windows 私钥或长期维护第二套服务器
  连接配置。

本地控制程序的默认入口是 CMD 中的交互式向导，而不是要求操作者拼接长命令或手写 JSON：

实际统一入口命名为 `uv run newton-test`，Windows 也提供 `newton-test.cmd`。当前可执行
链路只开放 Viewer、资产验收、本地 CPU 单案例摔落与固定 25° 坡度冒烟和只读结果浏览；下面的正式运行请求能力
仍是后续设计，不应从当前菜单中显示为可执行选项。

- 向导通过固定的只读远程命令取得可选资产，以及管理员配置的获授权 GPU 列表；
- 操作者依次选择资产、试验种类、运行配置、工况参数和获授权 GPU；
- 启动前必须展示服务器别名、资产、工况数量、关键参数、GPU 和预期产物的完整摘要，并
  取得一次明确确认；
- 确认后的结构化 **运行请求**自动保存在 Windows 本地，方便以后加载并重复相同选择；再次
  使用已保存请求时仍展示摘要并要求确认；
- 保存文件不包含私钥、真实服务器地址或任意服务器命令；服务器收到请求后独立执行资产、
  配置、参数和 GPU 授权校验，不能信任本地向导已经检查过的内容；
- 运行请求作为数据通过控制通道发送，不把资产路径、坡度或其他输入拼入 shell 命令；
- 第一阶段 Web UI 继续只负责浏览结果，不参与创建或启动试验。

真实资产不随 Git 仓库部署。本地数据集当前位于仓库之外，第一阶段使用 WinSCP 把需要测试的
完整资产包明确上传到个人账号获准使用的 **资产待导入区**：

- 本地控制程序不自动同步整个数据集，也不在启动试验时隐式上传文件；
- 每个上传包必须包含一个 `newton-mujoco.usda` 以及其完整、可解析的 USD、mesh 和纹理
  依赖；依赖逃出该资产包时验收入库失败；
- 待导入区允许存在尚未传完的目录，但这些目录永远不出现在正式运行的资产选择列表中；
- 上传完成后，操作者显式调用固定的 **资产验收入库**操作；服务器执行依赖解析、预检和
  内容哈希，全部通过后才把资产加入只读的正式资产库；
- 资产验收入库只接受待导入区中的相对目录，不接受任意绝对路径或 shell 文本；
- 正式资产库按内容保存不可变的 **资产版本**。同一内容重复验收入库可复用已有版本；内容
  变化会产生新版本，不覆盖已经用于试验的文件；
- **资产身份**使用验收入库时确定的规范化逻辑相对路径，不使用资产库内部的哈希存储路径；
- 待导入区、正式资产库和结果根目录都位于仓库之外，并由服务器本地配置指定；运行请求和
  结果只记录资产身份、资产版本及相对依赖，不记录绝对服务器路径。

向导为新运行请求默认选择该资产身份下最新入库的资产版本，并在确认摘要中显示入库时间和
版本短哈希。历史版本放在需要主动展开的选项中，不能因排序或文件修改时间被误选。已经
保存的运行请求固定完整资产版本哈希；再次加载时，如果该版本仍存在就使用原版本，不会
静默升级。操作者要检查新入库的物理参数时，必须新建请求或显式执行“更新到最新版”，然后
重新查看摘要并确认。

CMD 控制程序使用同一个主菜单提供“启动试验”“验收并加入资产库”“查看当前远程运行状态”
“打开结果浏览页”“检查服务器是否准备好”和“服务器存储设置”。服务器存储设置只配置一个
**服务器数据根目录**，服务器再管理固定子目录：

```text
<data-root>/
├── inbox/          # 资产待导入区
├── assets/         # 不可变正式资产版本
├── asset-trash/    # 已回收但尚可恢复的资产版本
├── import-reports/ # 资产验收入库报告
├── runtime/
│   ├── batches/    # 批次控制元数据
│   └── runs/       # 试验运行及产物
├── trash/          # 已回收的完整试验运行
└── web/            # 静态 Web UI 与结果索引
```

首次连接发现尚未配置时，向导推荐个人账号获准使用的持久化挂载下的目录，显示解析后的绝对
路径、文件系统和剩余空间，并在操作者确认后创建固定子目录。服务器拒绝把 `/`、用户主目录
本身、源码工作树、符号链接逃逸目标或已有无关内容的非空目录设为数据根目录；解析后的目录
还必须属于当前个人账号并位于服务器批准的存储范围。正式配置保存为个人配置文件
`~/.config/newton-test/server.toml`，文件权限限制为仅本人读写，仓库只提供不含真实路径的
示例。该个人配置只能保存存储和界面等个人设置，不能授予 GPU 权限或扩大管理员限制。
当前底层 `configure-storage` 要求批准目录已经存在并属于当前账号，还要求通过
`--confirm-admin-approved-path` 重复同一解析后路径；这只是操作者确认，不能代替管理员批准。
每条后续服务器命令继续复查目录存在性、所有权和写权限。

设置入口可以随时只读显示当前路径、各子目录用量和文件系统剩余空间。若正式资产、运行
结果或回收项已经存在，普通设置操作拒绝直接改变根目录，也不自动搬迁数据；以后需要迁移
时使用单独的停机、复制、校验和切换流程。服务器内部可把 `<data-root>/runtime` 暴露为
兼容环境变量 `NEWTON_RUNTIME_ROOT`，但它是由数据根目录派生的值，不能独立指向另一位置。

“检查服务器是否准备好”执行 **服务器就绪检查**，按 `passed`、`missing`、`blocked` 和
`warning` 报告至少以下内容：

- SSH 主机身份与固定命令连接；
- 服务器数据根目录、目录所有权、写入探针和可用空间；
- 已部署 Git commit、干净工作树、锁定 Python 3.12 环境和关键依赖；
- FFmpeg 与所需 H.264 编码能力；
- `allowed_gpu_uuids`、`default_gpu_uuid`、UUID 与当前可见设备的匹配、驱动和只读占用
  诊断，以及 GPU 策略是否由管理员控制而非当前用户可写；
- 两端回环绑定及 SSH 本地端口转发能否建立；
- 当前是否已有批次锁或活动运行。

就绪检查不导入 Newton 或创建 CUDA 上下文，不获取 GPU 锁，不运行仿真，不写入权限配置，
也不修改 Tailscale Serve。存储写入探针只在已经配置的数据根目录内创建一个随机命名的小型
临时文件并立即删除；若不能安全完成则报告失败。缺少管理员提供的 GPU 授权、获准存储位置
或其他外部条件时只列出缺项，不能猜测或代填。正式批次启动前必须再次执行等价的关键检查，
不能把较早的就绪报告当作永久授权。

就绪检查遇到管理员依赖项时，同时生成一份可复制的 **管理员确认清单**，默认使用中文纯
文本并保存在 Windows 用户应用数据目录。清单只包含当前缺失问题和项目预期行为，例如允许
的 GPU UUID 与默认设备、GPU 共享或忙碌规则、获准数据根目录与配额、SSH 本地端口转发、
服务器回环地址上的临时只读结果服务、私有仓库只读 Deploy Key 出站访问，以及运行时长或
并发限制。清单只记录 SSH 别名和项目名称，不包含真实服务器地址、私钥、令牌或已保存
凭据；程序不自动发送消息、创建工单或修改任何服务器权限。

正式资产版本采用显式保留和回收规则：

- 第一阶段不自动删除任何已经验收入库的资产版本；
- 正常结果和结果回收站中的运行都形成资产版本引用；只要存在任一引用，资产版本回收和
  永久清理都必须拒绝；
- 尚未验收入库的上传错误由操作者在 WinSCP 中清理 `inbox/`，不经过正式资产回收流程；
- 已入库但没有任何运行引用的错误版本，可以通过受限 CMD 资产库管理操作执行
  **资产版本回收**，原子移动到 `asset-trash/`，不立即删除；
- 回收前显示资产身份、完整版本哈希、占用空间和运行引用数量，并要求明确确认；
- `asset-trash/` 中的版本可以恢复；永久清理使用独立操作、再次确认，并且只接受资产身份
  和版本哈希，不接受路径、通配符或 shell 文本；
- 本地保存的运行请求不是服务器资产引用；请求固定的版本若已回收，服务器拒绝运行并提示
  先恢复该版本，不能静默改用最新版；
- 第一阶段 Web UI 不提供资产回收或永久清理入口。

资产验收入库以 `inbox/` 下直接包含 `newton-mujoco.usda` 的资产包目录确定资产身份。例如
`inbox/microwave/model-001/newton-mujoco.usda` 对应资产身份
`microwave/model-001`。同一相对目录中的新内容产生该资产身份的新版本；目录移动或改名
产生新的资产身份，系统不根据文件内容、显示名称或相似度猜测两者关系。

相对目录在验收时统一使用 `/` 分隔并执行 Unicode NFC 规范化；绝对路径、空路径段、`.`、
`..`、控制字符、符号链接逃逸以及与现有身份仅大小写不同的冲突都必须拒绝。规范化只用于
得到稳定身份，不改写上传包内部的 USD 引用或实际文件名。

验收入库通过后，服务器在同一文件系统内把完整资产包原子移动到正式资产库的不可变版本
位置，不复制并保留第二份。移动成功后，该目录从 WinSCP 可见的 `inbox/` 中消失，但内容
仍完整存在于 `assets/`；任一检查失败时，上传目录原样留在待导入区。若内容哈希与同一
资产身份下的现有版本完全相同，操作返回“版本已经存在”且不修改正式资产库，也不自动删除
待导入区中的重复副本，由操作者通过 WinSCP 明确清理。

本地数据集中的完整资产包是唯一可编辑来源。验收入库失败时，操作者根据报告在本地修正，
通过 WinSCP 明确清理对应的失败上传目录，再把完整资产包重新上传到相同相对目录；不在
服务器上直接修改 USD、mesh、纹理或物理参数，也不把修正内容覆盖合并进旧上传目录，因为
本地已经移除的依赖可能残留并被误纳入新版本。正式资产库和资产回收区中的内容始终只读，
任何物理参数修改都必须从本地形成新上传包并重新验收入库。

每次验收入库尝试都生成一份小型 **资产验收报告**。CMD 显示适合操作者阅读的中文摘要；
服务器把结构化原件保存在 `import-reports/<attempt-id>/report.json`，本地控制程序同时把
副本下载到 Windows 用户应用数据目录。报告至少记录尝试 ID、时间、规范化资产身份、状态、
文件数量、总大小、相对依赖、已完成的哈希、目标物理字段检查和稳定错误码；成功报告还记录
最终资产版本。报告不保存资产内容副本、绝对服务器路径、凭据或任意命令，第一阶段保留成功
和失败报告且不自动清理。若入库已经原子提交但本地报告下载失败，正式版本保持成功，CMD
明确提示可稍后重新下载服务器原件。

资产验收入库分为通用检查和逐试验模板的 **试验就绪状态**：

- 通用检查要求 `newton-mujoco.usda` 可打开、完整依赖位于资产包内、路径安全且内容哈希
  可以计算；通用检查失败时不能入库；
- `drop` 和 `slope_friction` 分别检查自身要求的质量、惯量、摩擦、接触参数和几何兼容性，
  产生独立的 `ready` 或 `not_ready` 状态及稳定原因码；
- 至少一个已批准试验模板为 `ready` 时允许验收入库；并非全部模板就绪时，该资产版本标为
  **部分就绪**；
- 所有已批准试验模板均为 `not_ready` 时验收入库失败，资产包留在 `inbox/`；
- 资产验收报告保存逐模板就绪表；就绪状态属于具体资产版本，并记录检查器版本和 Git commit；
- CMD 先选择资产身份，默认选择最新版本并显示该版本逐模板就绪表，再允许选择一个或多个
  `ready` 模板；历史版本需要主动展开；
- 同一运行请求选择多个模板时，该资产版本必须对每个所选模板都就绪；任一模板未就绪就
  禁用该组合并显示原因，不能静默跳过、缩减请求或强制绕过；
- 远程编排器收到运行请求后仍重新执行所选模板的关键检查；缓存的就绪状态不是运行授权；
- 部署更新改变模板要求或检查器版本后，现有版本的就绪状态需要重新评估，不能沿用过期
结论；
- `not_ready` 和 **部分就绪**只描述执行条件，不是资产物理质量判定，也不是试验执行失败。

一个经过确认的运行请求创建一个 **试验批次**。批次固定一个资产身份、一个资产版本、一个
运行配置和一次获授权 GPU 选择；每个所选任务模板分别创建一个独立 **试验运行**，因此一个
试验运行始终只属于一个任务模板。只选择一个模板时，批次仍存在但只包含一个运行。批次内
运行使用确定性顺序串行执行，不并发占用多块 GPU；每个运行拥有自己的运行 ID、状态、
`manifest.json`、工况目录和结果回收生命周期。

批次只负责表达“一次 CMD 确认提交了哪些运行”。Web UI 仍按资产和试验种类展示各个独立
运行；批次 ID仅作为辅助关联信息。摔落和斜坡运行可以单独重跑、回收或恢复，但单个运行
内部仍不能拆分删除工况。保存的运行请求固定输入而不是固定批次 ID；再次提交同一请求会
创建新的批次和新的运行 ID，不覆盖历史结果。

同时选择首版两个模板时，默认串行顺序为 `drop` 后 `slope_friction`，先用工况较少的摔落
运行确认加载、接触、渲染和编码链路，再进入工况较多的斜坡运行。CMD 确认页明确显示顺序并
允许操作者在提交前调整；运行请求固定最终顺序。批次不能并行执行两个模板，也不能自动改写
已确认顺序。

试验就绪状态与产生它的检查器版本和 Git commit 绑定。部署更新导致当前检查器标识变化时，
旧状态显示为 `needs_recheck`，不能直接授权运行；系统不因此自动扫描整个资产库。操作者在
CMD 选择资产版本或加载固定该版本的运行请求时，服务器按需执行 CPU 复查并追加一份新的
资产验收报告，不修改历史报告，也不占用正式 GPU。复查通过后，新状态可在相同检查器版本
下复用；若所有模板复查后均不就绪，已经入库的不可变资产版本仍保留，但不能创建运行请求，
不会被移回待导入区或自动回收。

现有 Windows `newton-env` Conda 环境保持不变，继续服务本地桌面 Viewer。新增
`pyproject.toml` 和提交到仓库的 `uv.lock`，作为 WSL 与远程 Linux 服务器的共同环境定义：

- Python 版本线固定为 3.12；
- 首版锁定已验证基线：Newton 1.4.0、Warp 1.15.0、MuJoCo 3.10.0、
  MJWarp 3.10.0.3、USD 26.3 和 `imageio-ffmpeg` 0.6.0；
- 测试、格式检查等开发工具放入独立依赖组，不混入服务器运行时最小依赖；
- WSL 与服务器都从同一份锁文件执行冻结安装，不根据安装当天的最新版本解析；
- `mujoco-cpu-wsl-smoke-v1` 与 `mujoco-native-dt1ms-v1` 共享 Python 依赖锁，只由命名
  运行配置选择 CPU/GPU 行为；
- 依赖升级必须显式更新锁文件、运行 WSL 冒烟测试，再通过远程 GPU 验收，不能原地静默
  升级服务器环境。

`uv.lock` 是提交到 Git 的依赖锁定清单，不包含实际安装包。第一阶段服务器就绪检查验证
管理员允许的 HTTPS 出站访问以及锁文件所需包源是否可达；部署使用 `uv sync --frozen`，
只能安装锁文件确定的版本和分发文件。若依赖无法下载或校验，正式部署保持阻止状态并报告
具体来源，不临时换版本、放宽锁定或忽略失败。

第一阶段不复制 WSL 虚拟环境到服务器，也不建设完整离线 Python 环境包。WSL 为 Ubuntu
24.04，目标服务器为 Ubuntu 22.04，不能假设二进制环境可直接搬运。若就绪检查以后证明
服务器长期无法获得依赖，再单独设计面向 Ubuntu 22.04、Python 3.12 和 x86-64、与
`uv.lock` 完全匹配且带哈希校验的离线依赖来源；这不属于首版范围。离线 Git bundle 只解决
代码传输，不能被误认为同时包含 Python 依赖。

代码部署只使用已经提交的 Git 版本。服务器工作树必须干净，并检出明确的 commit SHA；
运行清单记录该 SHA。不得把本地未提交工作树通过复制或 `rsync` 覆盖到服务器，也不得把
资产或运行结果放入 Git 仓库。

服务器能够访问 GitHub 时，私有仓库优先使用绑定到
`Cotsheep/Newton-Physics-Viewer` 的独立只读 Deploy Key：

- 私钥只保存在个人集群账号的受保护 SSH 配置中，公钥添加到该仓库；
- Deploy Key 不授予写权限，服务器只能 clone、fetch 和检出，不能 push；
- 服务器使用独立 SSH host 配置选择该密钥，不复用个人 GitHub 账号的通用 SSH 密钥；
- 首次连接必须核对 GitHub 主机密钥，不能关闭 host key 检查；
- Deploy Key、令牌和 SSH 配置不得进入仓库、日志、运行清单或结果目录；
- 个人 GitHub CLI 登录只允许临时诊断，退出后移除本地授权，不作为长期部署凭据。

若服务器无法访问 GitHub，允许使用 **离线 Git bundle 部署**作为备用传输方式：

- Windows 控制程序只接受完整 commit SHA，从本地 Git 对象库创建包含该已提交版本的
  bundle；当前工作树可以有其他改动，但未提交文件绝不进入 bundle；
- bundle 及其 SHA-256 通过现有 SSH 连接传入服务器部署暂存区，不使用 `rsync`、SFTP
  工作树覆盖或通用压缩包；
- 服务器先校验传输哈希并执行 `git bundle verify`，再确认请求的完整 commit 确实位于
  bundle 中；任何校验失败都不能改变当前部署；
- 校验通过后只把 Git 对象取入现有仓库并检出请求 commit，不接受 bundle 中的分支名作为
  最终选择依据；
- bundle 传输不要求服务器保存个人 GitHub 登录或 Deploy Key，也不改变“服务器工作树必须
  干净且运行清单记录准确 commit”的规则；
- bundle 只解决 Git 代码传输，不宣称解决 Python 包下载；依赖仍必须通过冻结锁文件和另行
  验收的在线或离线依赖来源安装。

第一阶段只允许通过普通 SSH 人工触发固定部署命令：

- 调用者必须传入完整 commit SHA，不接受分支名自动跟随或本地目录；
- 若 GPU 锁或运行状态表明仍有试验运行，部署立即失败；
- 在线模式通过只读 Deploy Key 执行 `git fetch`；离线模式校验并获取 Git bundle；两种
  模式随后都检出指定 commit，并确认服务器工作树干净；
- 使用 `uv sync --frozen`，锁文件与 commit 不一致或安装失败时停止；
- 在允许正式运行前执行服务器短时冒烟测试，并记录部署诊断；
- 第一阶段不配置 webhook、定时拉取、GitHub Actions 直连服务器或其他自动部署入口。

部署状态区分候选 commit 和上一个已验收 commit。已验收指针保存在源码工作树之外，只在
候选版本依赖同步和服务器冒烟测试全部成功后原子更新。任一步骤失败时，固定部署命令必须：

- 把单个服务器工作树恢复到上一个已验收 commit；
- 按旧 commit 的 `uv.lock` 再次执行冻结同步；
- 保持正式试验入口指向旧版本；
- 保存候选 SHA、失败阶段、退出码和部署日志；
- 不把失败候选标记为可运行版本。

第一阶段使用一个干净工作树完成部署和回滚，不引入多版本发布目录或自动清理策略。若恢复
旧环境也失败，则关闭正式试验入口并报告部署损坏，不能继续使用部分更新的环境。

因此 WSL 用于 Linux 行为、命令入口、配置校验、结果协议、静态 Web UI、进程管理以及可行的
MuJoCo CPU 短时冒烟测试。WSL 结果不作为批准的资产物理试验结果，也不能替代远程服务器的
NVIDIA GPU、无头渲染和编码验收。

## 2. 与现有代码的边界

现有本地查看器继续保留：

- `view.py` 仍是本地桌面 Viewer 的兼容启动入口；
- `asset_viewer/` 继续提供资产发现、模型构建、求解器、关节控制、相机、碰撞显示和
  牵引力等能力；
- 未使用远程试验入口时，现有本地 Viewer 的行为和交互不变。

服务器自动试验使用独立的 `run_physics_experiment.py`：

- 复用 `asset_viewer/` 的资产加载、模型构建、相机和渲染能力；
- 不启动桌面交互会话；
- 负责建立试验场景、推进仿真、输出预览、录制结果和写入运行清单；
- 可以复用 `record_collision_comparisons.py` 已有的无头取帧和 MP4 编码实现。

因此，“在服务器运行 `view.py`”在本项目中指复用 Viewer 背后的 Newton 仿真能力，而不是
把桌面窗口通过网络转发到本地。自动试验不复用本地 Viewer 当前的接触管线，试验结果也
不以本地 Viewer 的运动结果为一致性基准。

第一阶段只接受组合完成的 USD **试验资产**。每个资产的唯一入口文件名为
`newton-mujoco.usda`，它必须通过 USD sublayer/reference 等组合机制包含：

- `asset.usda` 中的几何、刚体、质量、惯量和其他基础资产信息；
- 新增的 MuJoCo 接触与摩擦参数；
- 试验运行所需的全部外部 USD、mesh 和纹理依赖。

Python 试验入口不接收一组 USD 文件并临时拼接 stage。预检必须确认
`newton-mujoco.usda` 可以独立打开、所有依赖可以解析，并且最终组合 stage 中能够读取
目标物理属性。运行清单记录该入口的规范化相对路径和完整依赖列表。

## 3. 第一阶段试验范围

物理检查方法来自
[`Newton–MuJoCo 3D 资产物理合理性仿真检查方案.md`](Newton–MuJoCo%203D%20资产物理合理性仿真检查方案.md)。

两项试验共同使用资产特征尺寸 `L`：

```text
L = 初始姿态下全部资产碰撞几何 AABB 的最大边长
L_eff = clamp(L, 0.10 m, 1.00 m)
```

计算时排除地面、坡道、参考物和纯视觉几何。选择最大边长而不是垂直高度，可避免薄盘、
长杆等资产得到没有观察价值的过小场景。斜坡长度、释放高度和尺度参考标记以
`L_eff` 为相对基准，实际资产投影尺寸用于保证场景几何确实容纳资产。运行清单同时记录
原始 `L`、`L_eff` 和最终场景尺寸。

两项试验默认保留资产声明的根朝向和关节初始状态，不自动关闭关节、不搜索稳定面，也
不按包围盒重新定向：

- 摔落试验只对整个资产做垂直平移，使最低碰撞点达到规定净空；
- 斜坡试验对整个资产施加与坡面一致的刚体旋转和平移，保持原始 yaw 和内部关节状态；
- 运行清单记录最终根变换和全部关节初始状态；
- 若以后需要特殊姿态，使用显式命名的资产姿态配置，不添加隐藏的自动修正。

每个独立坡度或释放高度默认推进 `10 s` 物理时间，允许配置为 `2–60 s`。录像中的
`0.5 s` 初始静止展示不计入物理时间。第一阶段不根据速度、位置或接触状态自动提前结束；
持续滚动、缓慢下沉和长期抖动本身都是需要保留的观察结果。

第一阶段不设置整次运行的固定墙钟硬上限。只要本地控制端保持在线，试验可以持续到所有
有限工况自然结束；不能因为经过 30 或 60 分钟就自动切断合法运行。结果页继续显示最后进展
时间并对长时间无更新给出警告，但警告本身不终止进程。

两项试验的中性参考面都使用 MuJoCo 原生支持的 plane 或 box primitive。其
`mjc:priority` 设置为资产所有碰撞体最小优先级再减一，使发生接触时资产一侧完整主导
friction、condim、`solref` 和 `solimp`，避免同优先级混合改变待测参数。若优先级无法
安全下调则预检失败，不静默改用混合值。运行清单记录参考面参数以及从 MuJoCo 模型读取
回来的最终接触参数。

### 3.1 斜坡摩擦试验

任务模板名：`slope_friction`

- 使用统一的中性参考面；
- 公共固定坡度默认为 `10°`、`25°`、`40°`；
- 运行参数允许用一套自定义固定坡度整体替换默认值；
- 自定义集合包含 1–12 个角度，每个角度必须满足 `0° < theta <= 80°`；
- 若资产具有有效的 `physics:dynamicFriction`，则计算预测滑动临界坡度并额外测试该角度
  本身及其上下偏移角度；
- 临界坡度偏移量 `delta_degrees` 可配置，默认 `5°`，允许范围为 `1°–15°`；
- 固定坡度先排序去重，再与预测滑动临界坡度邻域合并去重；
- 水平滑行段独立存在，`0°` 不属于坡度集合；
- 固定坡度、偏移角和允许的角度范围都必须经过校验并写入运行清单；
- 待测资产使用自身已标注的摩擦参数；
- 第一版释放策略为 `rest`：每个坡度从全新模型状态开始，资产位于坡面上方的极小安全
  间隙，初始线速度和角速度均为零，不施加推力或随机扰动；
- 录像先显示约 `0.5 s` 的静止初始画面，再开始推进物理；
- 设资产在坡面坐标系中的下坡方向尺寸为 `E_down`、横向尺寸为 `E_cross`，默认坡面长度
  为 `max(6 × L_eff, 3 × E_down)`，坡面宽度为
  `max(3 × L_eff, 1.5 × E_cross)`；
- 资产初始位置距坡顶至少 `1 × L_eff`，并在下坡方向保留至少 `5 × L_eff` 的运动距离；
- 水平滑行段长度为 `max(10 × L_eff, 5 × E_down)`；
- 坡面底边与水平段位置连续，不留台阶、缝隙或重叠，但第一版不添加圆弧平滑过渡；
- 坡面和水平段使用 MuJoCo 原生支持的实体 primitive，不使用平面 mesh；
- 不设置侧栏、终点挡板或把资产拉回场景的隐藏约束；资产横向离开坡面也作为结果保留；
- 记录开始运动、滑动、滚动、翻倒、减速和停止过程；
- 包含水平面滑行观察，用于辅助观察滚动摩擦表现。

该试验用于统一、直观地筛查明显过滑、过黏或滚动异常，不测量可适用于任意材料对的
真实摩擦系数。

预测滑动临界坡度使用理想斜面关系：

```text
theta_pred = degrees(arctan(physics:dynamicFriction))
```

中性参考面的设置必须使求解器最终使用的滑动摩擦不高于资产值。运行清单记录原始
`physics:dynamicFriction`、`theta_pred`、偏移角和最终实际坡度集合。该角度只预测理想
纯滑动开始条件；球形资产可能先滚动，高瘦资产可能先倾倒，求解器的接触混合与数值设置
也可能使实际开始运动角度偏离该值。超出合法坡度范围的邻域角度不静默钳制，而是跳过并
在运行清单中记录原因。结果页不得把 `theta_pred` 标为实测或真实临界坡度。

第一阶段按“每个资产一个摩擦数值”的检查方案工作。斜坡试验要求最终组合 stage 中存在
唯一、有限且非负的 `physics:dynamicFriction`，并显式包含待观察的
`mjc:rollingfriction` 和接触维数。缺失、非法或存在多个不同滑动摩擦值时预检失败，不
退化为只运行公共坡度，也不取平均值或任选一个。

释放策略是显式试验参数。第一版只实现 `rest`；若实际录像表明静止释放无法提供足够观察
信息，后续可增加具有固定线速度或角速度的命名策略。结果页和运行清单必须显示策略名及
完整参数，不能在不改变记录的情况下调整默认释放行为。

坡面长度、宽度、初始留边和水平段倍率也属于命名运行配置。实际观察需要调整时新增配置
版本，不修改已经产生结果的配置定义。

坡面—水平面连接几何同样写入运行配置和运行清单。若锐角底边冲击明显掩盖摩擦表现，
后续新增带圆弧过渡的配置，不修改第一版连接方式。

### 3.2 摔落试验

任务模板名：`drop`

- 使用统一的刚性水平参考面；
- 低、中、高三档释放高度分别为 `0.5 × L_eff`、`1.0 × L_eff` 和
  `2.0 × L_eff`；
- 释放高度指资产最低碰撞点与地面之间的垂直净空，不是质心高度；
- 资产从静止状态自由落下；
- 场景包含帮助判断尺寸和高度的参考物或标记；
- 记录首次碰撞、回弹、翻滚、穿透、抖动、下沉和最终稳定过程。

运行清单记录 `L`、`L_eff`、每档实际净空和由此得到的初始世界姿态。

该试验用于发现接触过软、过硬、回弹或阻尼明显异常，以及接触不稳定。它观察
`solref` 和 `solimp` 组合后的整体表现，不反推出某个字段的现实真值。

### 3.3 暂缓内容

- 浸水测试；
- 自动通过/不通过判定；
- body、joint 或 contact 的逐帧原始轨迹文件；
- 批量资产提交；
- 资产间自动排名或基线回归；
- 通过浏览器调整场景或运行中的物体；
- 新的物理字段标定方法。

第一阶段结果以可复现的人工观察材料为主，而不是自动质量结论。

- Web 与 Worker 服务拆分；

第一阶段 Web UI 是只读的 **结果浏览页**，不提供创建、取消、删除、重命名或修改操作。
结果根目录包含固定的静态 HTML/CSS/JavaScript，以及由远程启动器原子更新的
`index.json`。浏览器定时刷新：

- 根 `index.json`：资产索引、封面、该资产的运行状态摘要、试验种类和最近试验时间；
- 每次运行的 `status.json`：当前工况、进度、预览和失败摘要；
- 当前 `preview.jpg`：通过修改时间或查询参数绕过缓存。

首页采用类似视频网站的资产封面网格，而不是以运行清单作为主要入口。每张
**资产封面**简单展示资产外貌，并附带资产名称、已有试验种类、最近运行状态和时间。
点击封面进入该资产的 **资产试验页**。资产试验页将该资产的结果按
`slope_friction`、`drop` 等试验种类分区，再在各分区内按运行和工况组织录像。每个试验
分区默认展开最新一次运行；旧运行按开始时间倒序折叠，并显示时间、资产版本、运行配置、
最终状态和工况数量。新运行只追加结果，不覆盖或改写旧运行。

首页只索引至少存在一次未回收试验运行的资产，包括运行中、失败和成功结果。第一阶段不扫描
正式资产库来建立完整资产目录，也不为从未运行的资产批量生成封面。某资产的
全部运行进入回收站后，其封面从首页隐藏；恢复任意一次运行后，封面重新出现。

资产首次进入结果索引时，系统从该资产组合后的视觉外观自动生成独立封面：

- 16:9 画幅；
- 统一中性背景；
- 固定三分之四观察方向，并根据视觉边界自动调整相机距离；
- 只展示资产外貌，不带斜坡、释放高度标记或其他试验环境；
- 不使用某个工况的 `final.jpg` 代替资产封面；
- 第一阶段不要求上传或编辑自定义封面。

资产归档同时区分身份和版本：

- **资产身份**是 `inbox/` 下直接包含 `newton-mujoco.usda` 的资产包目录经过规范化后
  得到的逻辑相对路径；它不包含资产库内部的版本哈希目录；
- 首页每个资产身份只显示一个封面入口，物理参数更新不会产生重复入口；
- **资产版本**由入口文件及其完整依赖内容的 SHA-256 确定；
- 每次运行和每个工况视频都记录实际使用的资产版本；
- 新运行请求默认使用最新入库版本，历史版本需要主动选择；保存后的运行请求固定完整版本
  哈希且不随新入库版本自动变化；
- 资产包目录移动或重命名会形成新的资产身份，不自动猜测它与旧路径的关系。

每个已有录像的工况使用 **工况视频条目**呈现：以对应静态画面作为视频封面，显示工况
标签、运行状态和关键参数。播放同时支持两种入口：

- 点击视频画面中央，在当前资产试验页的卡片内直接加载并播放 `video.mp4`；
- 点击卡片标题或画面右上角的展开图标，进入该工况的独立 **工况播放页**并开始播放。

同一页面最多有一个卡片内播放器处于播放状态；开始播放另一工况时自动暂停前一个。未播放
卡片只加载静态封面，不预加载完整 MP4。独立工况播放页显示大尺寸播放器、资产名称、试验
种类、坡度或释放高度、资产版本、运行配置、状态和返回资产试验页的入口。两种播放方式
读取同一个结果 `video.mp4`，不复制或二次编码录像。

不以单独的“播放录像”文字按钮作为主要入口。下载录像、查看 JSON 和日志可以保留为次级
操作。运行中的工况使用当前预览画面和状态占位，尚未生成完整录像时不伪装成可播放。

资产试验页从各次运行的 `manifest.json`、`status.json` 和各工况的 `case.json` 读取
参数，并直接播放或下载 `video.mp4`。第一阶段不运行 FastAPI 或其他动态 Web 后端，也不
修改当前为空的 Tailscale Serve 配置。

CMD 控制程序提供“打开结果浏览页”，建立独立的 **按需结果浏览会话**：

- Windows 使用现有 `ssh.exe` 建立仅绑定本地 `127.0.0.1` 的本地端口转发，并通过已有
  SSH 别名连接服务器；
- 固定远程命令启动只绑定服务器 `127.0.0.1` 的只读结果服务，不能监听 `0.0.0.0`、
  Tailscale 接口或公网接口；
- 结果服务只允许 `GET` 和 `HEAD`，支持 MP4 字节范围请求，并把 URL 映射限制在
  `<data-root>/web` 和 `<data-root>/runtime/runs` 的允许读取范围内；
- 路径规范化后仍必须位于允许根目录，拒绝目录穿越、符号链接逃逸、任意文件读取和写请求；
- 控制程序在隧道就绪后打开本地回环地址；浏览器不接触服务器真实地址、用户名或远程端口；
- 浏览会话使用独立 SSH 子进程，与试验批次控制连接互不影响；关闭页面、浏览会话或隧道
  不会停止试验，取消试验也不修改已有 Web 文件；
- 实时试验时使用两个由操作者看得见的 CMD 窗口：窗口 A 前台控制试验批次，窗口 B 前台
  维持结果浏览会话；同一个 Windows 控制程序可以在两个窗口中分别选择对应操作；
- 窗口 B 显示本地浏览地址、明确说明只读服务不启动 GPU 物理仿真，而本地浏览器播放视频
  仍可能使用本机图形加速，并等待操作者按 `Ctrl+C` 或关闭窗口后结束；浏览器标签关闭本身
  不被当作可靠的隧道关闭信号；
- 不创建隐藏浏览进程。关闭窗口 B 只结束结果访问，关闭或取消窗口 A 才影响试验批次；
  只查看历史结果时只需要窗口 B；
- SSH 连接关闭时远程只读结果服务必须退出，不能用 `tmux`、`nohup` 或守护方式遗留；
- 第一阶段只有持有操作者个人 SSH 凭据的本地控制程序可以打开结果页，不提供共享链接。

一个试验运行中的每个工况由编排进程在独立子进程中执行：

- 单个工况失败时保留该工况日志和原因，然后继续尚未开始的工况；
- 全部工况成功时运行状态为 `succeeded`；
- 至少一个工况成功且至少一个失败时为 `partially_succeeded`；
- 没有工况成功时为 `failed`；
- 用户取消时终止当前工况的完整子进程树，不再启动后续工况，状态为 `cancelled`；
- GPU 或驱动健康检查失败时停止后续工况，并将运行标为 `failed` 或
  `partially_succeeded`，取决于是否已有成功工况。

这些状态只描述执行完整性，不表示资产物理质量通过或不通过。

批次编排器按失败作用域决定是否继续：

- **工况级**错误只结束当前工况，记录失败后允许当前运行继续后续工况；
- **运行级**错误结束当前任务模板的运行；只要资产版本、GPU、驱动、磁盘和结果协议仍
  健康，批次允许继续下一任务模板；
- **批次级**错误立即阻止全部未开始运行，包括资产运行中变化、GPU 或驱动健康检查失败、
  GPU 竞争、磁盘空间不足、结果目录或完整性协议损坏；
- 未分类异常默认按批次级错误处理，不能乐观继续；
- `Ctrl+C` 把批次标为 `cancelled` 并立即终止当前工况进程组；控制连接失效允许当前有限
  工况收尾，但把批次标为 `interrupted` 且不启动任何后续工况或运行。

批次状态保存每个运行的独立状态，并提供 `succeeded`、`partially_succeeded`、`failed`、
`cancelled` 或 `interrupted` 的聚合摘要。聚合摘要不改写子运行状态；取消或中断即使已经
产生部分成功结果，主状态仍保持 `cancelled` 或 `interrupted`，同时显示已完成运行和工况
数量。

### 4.1 远程进程托管

当前服务器没有调度器或 systemd，第一阶段采用 **SSH 工况边界控制后端**：

- 本地控制程序调用现有 OpenSSH 客户端，以固定命令提交一个试验批次；
- 每个工况仍由独立子进程执行，Python、渲染器和 FFmpeg 位于可整体终止的进程组；
- 远程编排器完成一个工况后，先原子完成录像、截图、JSON 和状态，再向本地发送
  `case_finished` 事件；
- 除批次最后一个工况外，本地控制端必须回复包含正确批次 ID、运行 ID 和工况 ID 的
  `continue`；
- 远程端最多等待 `60 s`；连接关闭、消息错误或确认超时均写入
  `controller_ack_timeout`，运行状态为 `interrupted`，不启动后续工况；
- 控制端在工况执行中失联时，当前工况允许完成并保存；完成后其子进程退出并释放 GPU
  显存，再进入续行确认；
- `Ctrl+C` 由本地控制程序转换成显式取消消息，远程端立即终止当前进程组并写入
  `cancelled`；
- 协议使用独立的结构化标准输入/输出通道，普通日志只写 `run.log` 和标准错误，不能与
  控制消息混写；
- 启动前使用 `flock` 实现本项目的单批次排他；批次串行运行期间持续持有锁，锁被占用时
  第二次启动立即失败；
- 第一阶段不使用持续心跳、总墙钟硬上限、linger、systemd、`tmux`、`setsid`、`nohup`
  或自建常驻守护进程。

这不是让工况脱离控制长期运行：失联后只允许已经开始的一个有限工况收尾，续行确认缺失时
整个批次退出。若以后需要整个批次自主继续，必须新增受管后台后端并单独验收。

## 5. 运行配置

任务模板定义“做什么”，运行配置定义“在什么仿真条件下做”。

浏览器或命令行操作者不能自由组合求解器和数值参数。每次试验必须选择服务器预先批准的
命名运行配置；第一阶段默认配置使用 MuJoCo。运行配置完整限定：

- 求解器；
- 帧率和物理时间步；
- substeps 和 iterations；
- 地面、重力和根节点策略；
- 渲染尺寸、相机和预览间隔；
- 每个试验模板允许的其他固定条件。

第一阶段默认运行配置采用 MuJoCo 原生接触：

```text
profile = mujoco-native-dt1ms-v1
SolverMuJoCo(use_mujoco_contacts=True, iterations=10)
physics_dt = 0.001 s
video_fps = 50
physics_steps_per_video_frame = 20
video_resolution = 1280x720
video_codec = H.264
video_pixel_format = yuv420p
video_crf = 18
preview_resolution = 640x360
preview_interval = approximately 1 s
```

### 5.1 GPU 授权与选择

服务器直接可见多块 GPU，但“可见”不代表操作者获准使用，用户可写配置中的允许列表也不能
证明授权。正式试验要求存在管理员控制的 **GPU 授权策略**，通过下面至少一种方式实现：

- 容器或设备层只向个人账号暴露获授权 GPU；
- 管理员提供一个当前用户只能读取、不能修改的策略文件。

策略明确列出 `allowed_gpu_uuids`，并从中指定唯一的 `default_gpu_uuid`；任一项未配置、
默认值不在允许列表中、UUID 无法解析，或策略文件由当前用户拥有或可写时，正式 GPU 试验
拒绝启动。策略文件的具体绝对路径由服务器管理员提供，不进入仓库或运行结果。

- 优先用 NVIDIA GPU UUID 表示授权设备，不依赖可能重新排序的数字索引；
- CMD 向导预选管理员指定的默认 UUID，并在确认页显示型号、UUID 短标识、显存与当前计算
  进程占用；运行请求仍保存完整 UUID；
- 若默认 GPU 忙碌或健康检查失败，启动立即拒绝，不自动回退到另一块空闲设备；
- 允许列表含多块设备时，操作者可以在提交前主动改选另一块获授权 GPU，并在摘要中再次
  确认；程序不能替操作者做负载均衡；
- 每次启动必须让运行请求显式包含一个允许列表中的 UUID，并在导入 Warp/Newton 前设置
  设备可见性；
- 运行清单记录物理 GPU UUID、型号、驱动版本和进程内逻辑设备编号；
- 不自动选择“看起来空闲”的 GPU，不默认占用设备 0，也不跨多块 GPU；
- 每个允许的 GPU UUID 使用独立 `flock`，防止本项目在同一设备上重复启动；
- 第一阶段默认要求目标 GPU 独占空闲：发现其他计算进程、无法解释的显存或利用率占用，
  或无法可靠读取进程信息时拒绝启动；不排队等待，也不自动切换设备；
- 具体空闲采样窗口和显存阈值属于管理员策略；缺少明确阈值时采用保守默认并由服务器 GPU
  集成验收校准，不能根据一次试验临时放宽；
- `flock` 只能阻止 Newton-Test 自身在同一 UUID 上重复运行，不能代替对其他进程的诊断，
  空闲检查也不能代替服务器所有者的授权；
- 只有管理员策略明确允许 GPU 共享并定义允许进程、显存和利用率规则后，才可增加共享模式；
  第一阶段控制程序自身不能打开共享；
- 正式运行期间持续低频检查目标 UUID；若出现新的非本批次计算进程或策略外占用，写入
  `gpu_contention_detected`，允许当前有限工况保存为诊断产物但不标为有效成功，随后在工况
  边界停止整个批次；
- 程序永远不向其他用户进程发送信号，也不尝试释放不属于本批次的显存；
- 运行清单记录生效策略的非敏感版本标识或内容哈希，以及实际设备 UUID；不记录策略文件
  绝对路径；
- 如果管理员只通过口头或消息告知 UUID，而未提供设备隔离或不可写策略文件，CMD 可在
  “个人安全保护模式”下显示和检查这些 UUID，但该模式不能开启正式 GPU 试验；
- 第一阶段在服务器所有者提供受管理员控制的允许列表和默认 GPU UUID 前，正式 GPU 试验
  保持禁用；WSL CPU 冒烟、服务器就绪检查、资产验收入库和结果浏览不因此禁用。

本地 WSL 使用独立且不可与正式结果混淆的冒烟配置：

```text
profile = mujoco-cpu-wsl-smoke-v1
SolverMuJoCo(
    use_mujoco_cpu=True,
    use_mujoco_contacts=True,
    iterations=10,
)
physics_dt = 0.001 s
execution_tier = development_smoke
authoritative = false
case_duration = 2 s
initial_video_hold = 0.5 s (not counted as physics time)
video_fps = 50
video_resolution = 640x360
video_codec = H.264
preview_resolution = 320x180
preview_interval = approximately 1 s
drop_cases = [1.0 * L_eff]
slope_cases = [25 deg]
```

该配置保持 MuJoCo 原生接触和正式配置相同的物理时间步，以尽早发现接触字段、场景构建和
步进逻辑错误；每个模板只运行一个代表工况，并以两秒物理推进、低分辨率输出缩减 CPU 负载。
当前两个本地入口均已实现；坡度入口固定为 25°，只报告非正式的
`moved`、`stayed_near_start` 或 `inconclusive` 开发观察，不实现本路线后文定义的正式多角度、
预测临界坡度邻域或水平滑行段。
录像额外包含 0.5 秒初始静止展示。Linux 冒烟在导入仿真栈前隐藏 CUDA，将 Warp 固定为 CPU，
强制 Mesa 软件 OpenGL，并在任何物理步之前核对实际 OpenGL renderer；无法证明软件渲染时
失败关闭，不回退到服务器 NVIDIA GPU。运行
清单、状态文件、资产页面和工况播放页必须显著显示“本地冒烟测试，不是正式物理试验结果”，并记录
`use_mujoco_cpu=true`、`authoritative=false` 和实际硬件。冒烟结果不能参与正式运行比较，
也不能被标记为资产物理检查成功。

试验入口使用 MuJoCo 自身的碰撞检测和接触参数混合，使资产显式声明的 `mjc:solref`、
`mjc:solimp`、`mjc:condim`、摩擦及其他 MuJoCo 接触字段按原生路径生效。它不得照搬
当前 `view.py` 在 `use_mujoco_contacts=False` 下调用 `model.collide()` 并传入 Newton
contacts 的步进循环。

该配置每秒严格推进 1000 个物理步，每 20 步录制一帧。若资产显式声明的
`mjc:solref.timeconst < 0.002 s`，试验仍把原值交给 MuJoCo，但在结果页和运行清单中写入
`solref_timeconst_below_2dt` 警告，提示 MuJoCo 可能应用原生安全钳制；试验入口不得静默
修改资产参数。其他时间尺度必须通过新增命名运行配置提供，不能原地改变
`mujoco-native-dt1ms-v1` 的含义。

运行清单必须记录 `use_mujoco_contacts=true`、Newton/MuJoCo 版本及所有展开后的原生
接触配置。第一阶段集成测试至少验证：

- 修改资产的 `mjc:solref` 或 `mjc:solimp` 会改变摔落试验的可观测结果；
- 修改 `physics:dynamicFriction` 会改变理想斜面附近的运动表现；
- 本地 Viewer 与自动试验使用不同接触管线时，系统不会把两者结果标记为可直接比较。

试验启动前必须让 MuJoCo 原生接触路径完成资产兼容性预检。若资产包含原生路径不支持的
平面 mesh 或其他碰撞表示：

- 不自动凸化、加厚、替换或删除碰撞几何；
- 不退回 `use_mujoco_contacts=False`；
- 创建并保留该次运行目录、运行清单和诊断日志；
- 状态写为 `failed`，原因码写为 `unsupported_native_contact_geometry`；
- 结果页说明这是 **试验执行失败**，不是资产物理质量不合格；
- 用户修正资产后创建一次新的试验运行。

预检还必须确认试验目标字段均由 `newton-mujoco.usda` 的最终组合 stage 显式提供：

- 每个动态 link 具有有效的 `physics:mass`、`physics:centerOfMass`、
  `physics:diagonalInertia` 和 `physics:principalAxes`；
- `slope_friction` 具有唯一有效的 `physics:dynamicFriction`，并显式提供
  `mjc:rollingfriction` 与合法的 `mjc:condim`；
- `drop` 的每个参与碰撞 shape 都显式提供合法的 `mjc:solref` 和 `mjc:solimp`。

字段缺失时状态为 `failed`，原因码为 `missing_required_physics_attribute`；字段类型、
长度、范围或物理合法性错误时原因码为 `invalid_required_physics_attribute`。试验入口
不得用 MuJoCo 或 Newton 默认值填补这些必需字段。其他不属于当前试验目标的字段可以记录
警告，但不自动产生资产质量判定。

任务可以只开放少量经过范围校验的参数，例如资产路径。每个运行清单同时保存运行配置名
和展开后的完整参数，避免配置日后改变导致历史结果失去含义。

## 6. 结果协议

建议目录：

```text
runtime/
├── batches/
│   └── <batch-id>/
│       ├── batch.json
│       └── status.json
└── runs/
    └── <run-id>/
         ├── index.html
         ├── manifest.json
         ├── checksums.sha256
         ├── status.json
         ├── run.log
         ├── preview.jpg
         └── cases/
             ├── 001-<case-label>/
             │   ├── case.json
             │   ├── video.mp4
             │   ├── poster.jpg
             │   └── final.jpg
             └── ...
```

`batch.json` 至少记录批次 ID、运行请求摘要、资产身份与版本、运行配置、按执行顺序排列的
任务模板和运行 ID，以及创建时间。批次 `status.json` 记录当前运行、整体进度和各运行状态
摘要；它不是视频结果包，也不是结果回收单位。

### 6.1 `manifest.json`

至少记录：

- 不重复的运行 ID；
- 所属批次 ID；
- 试验模板名；
- 资产验收入库时确定的规范化逻辑相对路径形成的资产身份；
- 由入口及完整依赖内容确定的资产版本；
- `newton-mujoco.usda` 的规范化相对路径及完整 USD 依赖列表；
- 每个资产依赖的文件大小和 SHA-256；
- 运行配置名及展开后的完整参数；
- 创建、开始和结束时间；
- Git commit；
- Python、Newton、Warp、MuJoCo、CUDA 驱动和 GPU 信息；
- 结果文件名；
- 子进程退出码和失败摘要。

### 6.2 `status.json`

只记录浏览器查看所需的小型当前状态：

- `created`、`running`、`succeeded`、`partially_succeeded`、`failed`、`cancelled`
  或 `interrupted`；
- 当前试验阶段和进度说明；
- 当前工况及已完成工况数量；
- 最后更新时间；
- 预览图最后更新时间；
- 完成后的结果文件列表；
- 简短失败摘要。

状态文件和预览图都先写入同目录临时文件，再原子替换正式文件，避免浏览器读取到半写入
内容。

### 6.3 完整性校验

预检解析 `newton-mujoco.usda` 的全部依赖后，对入口及每个依赖计算 SHA-256，并把相对
路径、文件大小和哈希写入 `manifest.json`。仿真期间监控这些文件的大小和修改时间；若
发生变化，停止运行并报告 `asset_changed_during_run`，不把混合两个资产版本的结果标为
成功。

运行完成后生成 `checksums.sha256`，覆盖工况视频、截图、JSON、日志和 manifest，但不
包含校验文件自身。每个哈希只有很小的文本开销；即使依赖数量很大，校验清单也远小于
录像。结果浏览页提供校验文件下载，但不在浏览器中重新计算大型文件哈希。

### 6.4 结果录像

- 结果录像是主要视觉产物；
- 每个坡度或释放高度是一个独立 **工况**，生成自己的 `case.json`、`video.mp4` 和
  `poster.jpg`、`final.jpg`；
- 第一阶段不拼接总览视频；结果浏览页先按资产、再按试验种类统一组织各工况录像；
- 每个已完成工况以带静态画面的 **工况视频条目**呈现，点击画面直接在页面中播放录像；
- 每个工况还提供独立播放页；卡片内播放与独立播放页复用同一个 `video.mp4`；
- 资产试验页同一时间只播放一个卡片内视频，未播放卡片不预加载完整录像；
- 纯文字链接只作为下载或无障碍访问的辅助入口，不作为主要播放交互；
- `poster.jpg` 使用仿真开始前、场景与相机已经就位的固定总览画面，保证资产和坡度或释放
  高度上下文可见；
- `final.jpg` 只记录仿真结束时的最终状态，不作为默认视频缩略图；
- 预览只用于确认试验正在正常运行，建议约 1 FPS；
- 录像使用固定相机和批准的分辨率、帧率；
- 工况录像默认为 `1280×720`、`50 FPS`、H.264 MP4、`yuv420p`、CRF 18、无音频；
- 运行中预览默认为 `640×360` JPEG，约 1 FPS；
- 浏览器直接播放原始工况视频，不在结果服务端或浏览器中二次转码；
- 斜坡录像完整覆盖坡面、水平段和尺度标记；
- 摔落录像完整覆盖初始释放位置、地面和高度标记；
- 相机方向在对应试验的局部坐标系中固定，只在试验开始前根据场景边界调整距离；
- 仿真推进期间相机不平移、不缩放、不跟踪资产，资产离开画面也保留原结果；
- 场景中的尺度标记必须在录像中可见；
- 每个 `case.json` 记录实际坡度或高度、初始状态、运行配置和对应文件；
- 工况目录按确定性顺序编号，显示标签不作为唯一标识。

第一阶段不生成 `trajectory.npz`、逐帧 CSV 或其他 body/joint/contact 原始轨迹文件。
结果协议只保留观察所需的视频、截图、预览，以及解释运行条件所需的 JSON 和日志。

若以后需要接触特写，新增第二个命名相机视角；固定总览录像继续保留为跨运行比较基准。

## 7. 安全边界

- 服务器不开放公网 Web 端口；
- 第一阶段不配置 Tailscale Serve 或 Tailscale Funnel；
- 第一阶段结果服务只监听服务器 `127.0.0.1`，浏览器只连接 Windows `127.0.0.1`，二者
  通过经现有 Tailscale 私有地址建立的 SSH 隧道连接；
- 第一阶段结果访问沿用操作者个人 SSH 身份，实际结果查看者只有操作者本人，不创建共享
  Web 凭据或共享链接；
- 后期 Tailscale Serve 访问采用默认拒绝的命名授权，不因用户属于 tailnet 就自动放行；
- `result-viewers` 只包含明确指定的后期结果查看者；
- `result-maintainers` 是查看者中的更小子集，只在后期允许回收和恢复完整运行；
- 公网用户、匿名用户和其他 tailnet 成员不能浏览结果；
- 后期通过 tailnet 访问策略限制结果服务；集群 SSH 继续使用管理员批准的现有访问策略；
- 资产源目录使用服务器文件权限保持只读；
- 运行结果写入独立可写目录；
- 远程执行使用操作者的个人集群账号，不创建共享服务账号，也不增加 `sudo` 权限；
- 资产参数只接受配置资产根目录内的规范化相对路径；
- 自动试验入口不接受任意 shell 文本；
- 仓库不保存服务器真实路径、tailnet 信息或密钥。
- 服务器 Git 凭据只允许读取当前仓库，不具有推送或访问其他私有仓库的权限；

### 7.1 结果保留与清理

- 第一阶段不自动删除任何试验运行；
- 结果浏览页显示每次运行占用空间和结果盘剩余空间；
- 管理员策略可指定 `minimum_free_gib`；未指定时首版默认必须保留 `100 GiB`，个人可写
  配置不能把管理员下限调低；
- 启动前根据工况数量、每个工况时长、录像规划码率、截图、日志和结果元数据估算批次输出
  上界，并额外预留一倍临时编码与原子收尾空间；
- 只有预计批次完成后仍高于有效安全余量时才允许启动；估算公式、输入和最终要求空间写入
  启动诊断与批次元数据；
- 运行期间低频监控 `NEWTON_DATA_ROOT` 所在文件系统和可获得的个人配额信息；跌破安全线时
  尽力完成当前有限工况的可恢复收尾，但不再启动后续工况或运行；
- 若继续写当前工况会触及硬错误或无法安全完成 MP4，立即停止该工况并标记
  `insufficient_storage`，保留已有诊断，不能继续消耗空间；
- 空间不足时不自动回收或永久删除旧结果、资产版本、验收报告或回收站内容；
- 第一阶段结果浏览页保持只读，不提供删除按钮；
- 一个已经停止的试验运行是不可拆分的结果包，不允许单独删除其中的 `video.mp4`、截图、
  JSON、日志或校验文件；
- **结果回收**只能通过管理员批准的现有普通 SSH 连接调用专用命令；
- 回收命令只接受运行 ID，解析并验证目标为
  `NEWTON_DATA_ROOT/runtime/runs/<run-id>`，并拒绝回收仍在运行的试验；
- 回收操作把完整运行原子移动到 `NEWTON_DATA_ROOT/trash/`，不立即永久删除；
- 永久清理只能通过另一个显式命令按回收项 ID 执行，不自动清空回收站；
- 清理命令不接受任意目录、通配符或未经验证的递归路径；
- 回收、恢复或永久清理完成后原子重建根 `index.json`。

资产版本的回收与结果回收是两套独立操作。结果回收不会自动回收其资产版本；只有引用该
版本的全部正常结果和结果回收项都已经永久清理后，资产版本才可能成为可回收状态。资产
版本回收同样先进入可恢复区域，不允许通过任意文件路径直接删除。

### 7.2 后期 Web 回收

管理员明确批准持久 Web 入口和 tailnet 策略后，可以用 Tailscale Serve 替换第一阶段的
按需 SSH 隧道，并在结果浏览页加入“移入回收站”和“恢复”操作；这不是静态页面直接修改
文件。届时由 Tailscale Serve 反向代理一个只监听 `127.0.0.1` 的小型结果管理服务：

- Tailscale 访问策略先限制可访问服务的用户；
- 服务只接受由 Serve 注入且属于 `result-maintainers` 的用户身份执行写操作；普通
  `result-viewers` 保持只读，缺少身份、来自标记设备或身份不匹配时拒绝写操作；
- 写操作验证同源请求或防伪令牌，并记录操作者、时间、运行 ID、动作和结果；
- 页面只提交运行 ID 和幂等请求 ID，不提交服务器路径；
- 服务复用 SSH 清理命令的同一套路径验证、运行状态检查和原子移动逻辑；
- Web UI 只能回收或恢复完整、已经停止的试验运行，不能删除单个工况视频；
- 永久清理回收站仍只允许通过管理员批准的现有普通 SSH 路径执行；
- 结果管理服务对资产源目录没有写权限，也不接受任意 shell 文本。

这一阶段把部署形态从纯静态文件服务扩展为身份感知的本地写服务，因此必须单独验收访问
策略、身份头不可绕过、跨站请求防护、路径逃逸防护、并发回收和审计日志。

## 8. 第一阶段验收条件

- 本地 `view.py` 的功能和交互保持不变；
- 操作者可通过管理员批准的现有普通 SSH 路径启动 `slope_friction` 或 `drop`，共享服务器
  第一阶段不启用 Tailscale SSH；
- 本地控制连接正常时逐工况执行；控制端失联时只允许当前工况收尾，未收到续行确认不得
  启动下一工况，并留下 `interrupted` 状态；
- 任意时刻最多运行一个 GPU 试验；第二个启动请求立即得到明确的占用错误；
- 操作者可在前台 SSH 会话中通过 `Ctrl+C` 取消试验，完整进程树被终止；
- 服务器使用默认 MuJoCo 运行配置和 NVIDIA GPU 无头执行试验；
- 自动试验明确使用 `use_mujoco_contacts=True`，并在运行清单中记录；
- 本地浏览器只能通过绑定两端回环地址的按需 SSH 隧道查看运行中的低频预览；
- 实时查看时试验控制和结果浏览分别运行在两个可见 CMD 窗口；关闭浏览窗口不影响试验，
  且浏览会话不占用 GPU；
- 试验完成后可以在浏览器播放或下载结果录像；
- 每次运行都有独立目录、日志、最终截图、状态和完整运行清单；
- 结果页刷新或关闭不会影响服务器上的试验；
- 已停止的完整运行可通过受限 SSH 命令移入回收站并恢复，结果页本身不能删除结果；
- 资产路径无法逃逸配置的资产根目录；
- 服务器没有因结果查看功能暴露公网入口；
- CMD 可以在不运行 Newton/CUDA 的情况下执行服务器就绪检查；正式启动在关键检查未通过
  时拒绝，而不是尝试自动修复服务器；
- 失败运行保留日志和失败摘要，不伪装为成功结果。
- 原生 MuJoCo 不支持的资产明确报告 `unsupported_native_contact_geometry`，不被自动
  修改或切换接触管线；
- 缺失或非法的目标物理字段在仿真前明确失败，不使用后端默认值继续运行；
- 通用资产检查通过且至少一个试验模板就绪的版本可以入库；CMD 对未就绪模板禁用启动并
  显示原因，服务器不能被构造请求绕过；

指定：

- `NEWTON_DATA_ROOT`：唯一可配置的服务器数据根目录；
- `NEWTON_RUNTIME_ROOT`：由数据根目录固定派生为 `<data-root>/runtime` 的兼容值；
- `NEWTON_PREVIEW_INTERVAL`：预览间隔；
- `NEWTON_PREVIEW_WIDTH` / `NEWTON_PREVIEW_HEIGHT`：预览尺寸。

## 10. 实现顺序

1. 修复本地 WSL 网络，新增 `pyproject.toml` 与 `uv.lock`，并建立隔离、可复现的
   Python 3.12 Linux 环境；
2. 在 WSL 实现并验证服务器数据根目录设置、固定子目录、资产待导入区、验收入库、
   资产验收报告、逐模板试验就绪状态、不可变资产版本、引用保护、资产版本回收、结果协议
   和静态 Web UI；
3. 在 WSL 增加单元测试、进程管理测试以及可行的 MuJoCo CPU 短时冒烟测试；
4. 在目标 Linux NVIDIA 服务器探测 Newton、Warp、MuJoCo 原生接触、ViewerGL 无头渲染
   和 FFmpeg；
5. 从现有录像程序提取可复用的无头取帧与编码能力；
6. 实现 `drop`，先验证多高度录像与稳定结束；
7. 实现正式 `slope_friction` 多坡度、预测临界坡度邻域和水平滑行录像；本地固定 25°
   单案例 CPU 冒烟已经实现，但不等价于本项正式能力；
8. 生成静态结果页和低频预览；
9. 实现绑定两端回环地址、支持 MP4 字节范围请求且随 SSH 会话退出的按需只读结果服务和
   Windows SSH 隧道入口；
10. 实现当前 Docker 服务器的 Windows CMD 交互式控制向导、可复用运行请求、服务端
    二次校验、服务器就绪检查、工况续行确认、`flock` 单批次限制、信号处理和状态收尾；
11. 实现指定 commit、只读 Deploy Key 或离线 Git bundle 传输、冻结依赖、运行中拒绝
    更新和服务器冒烟测试组成的人工部署命令；
12. 在远程服务器执行 GPU 集成测试和最终验收。

WSL 是首个开发测试门槛，远程服务器是物理试验的最终验收门槛。目标服务器的 GPU 驱动、
EGL/OpenGL、Newton ViewerGL 和编码器组合未经验证前，不假设无头录像一定可用。

## 11. 后续升级条件

### 11.1 浏览器提交与任务队列

只有需要在浏览器创建、排队、取消和筛选多次运行时，才增加：

- FastAPI 与服务端页面；
- SQLite 运行索引；
- 单 GPU Worker；
- 状态与日志流；
- 经过批准的命令和参数映射。

届时浏览器仍不能提交任意 shell 命令，结果目录协议和
`run_physics_experiment.py` 保持不变。

### 11.2 批量检查与结构化指标

只有人工逐个查看录像成为瓶颈后，才增加：

- 一批资产和多配置矩阵；
- 父运行与子运行关系；
- 结构化指标、阈值和判定结果；
- 失败重试、结果比较和基线回归；
- 可导出的质量报告。

### 11.3 多 GPU、多服务器与多人协作

只有单 GPU 和单操作者成为实际瓶颈后，才评估：

- 每块 GPU 一个 Worker；
- PostgreSQL、Redis/Celery 或其他分布式调度；
- 共享对象存储；
- 用户、角色、项目、配额和审计日志；
- 独立 OIDC、监控、告警和高可用部署；
- Kubernetes。
